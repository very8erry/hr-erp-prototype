## 수정 후 검증 통과

각 문제의 수정 전 테스트는 실제 실패(Missing expected rejection 또는 검토 로그 부재)를 확인했다.

1. 다중 회사가 저장된 경우 companyId 보완 함수가 일찍 반환해 검토 로그도 생략했다. 자동 추정은 계속 금지하되 검토 로그를 최초 한 번 남기도록 수정했다.
2. ATS 전환이 존재하기만 하는 다른 회사 조직을 수락했다. 현재 회사와 조직 회사 일치를 확인하며 잘못된 입력은 트랜잭션 취소한다.
3. 인사발령이 존재하지 않는 조직을 저장했다. 발령 전 조직 존재와 Employment.companyId 일치를 확인한다.
4. 같은 날의 두 번째 즉시 인사발령이 이전 이력 종료일을 시작일보다 과거로 만들었다. 현재 이력 시작일과 같거나 이전인 신규 발령을 명시적으로 거부한다. 같은 날 복합 발령을 병합하거나 원본을 덮어쓰지 않는다.
5. 일용직 등록에 기존 personId를 넘기면 기존 Person의 이름/생년월일 등 원천정보를 put으로 덮어썼다. 신규 Person/일용직 저장을 add로 변경하고 실패 시 전체 취소한다. 기존 Person 재사용 기능을 구현한 것이 아니다. 기존 ID 재사용 호출은 이제 오류다.

## 추가 검증 필요 / 잔여 위험

- 예약 발령: createPersonnelAction은 현재 이력과 비교하지만, 동일 날짜의 여러 SCHEDULED 발령 사이 충돌 및 applyDueEvents 실행 시점의 재검증까지 해결하지 않았다. 기존 예약자료를 자동 변경하지 않았다. 병합 전 별도 충돌 테스트와 안전한 보류 절차 필요.
- 인사발령 조직 검사와 적용이 단일 트랜잭션으로 묶이지 않은 기존 경로가 있다. 다중 탭 조직 변경/동시 발령 경합은 미검증.
- 다중 회사: 누락 회사 소속은 검토 로그로 남기지만 앱 전체가 다중 회사 지원을 보장하지 않는다. exportDatabase의 company는 단일 객체다. 이번 테스트를 다중 회사 백업 지원 판정으로 사용하면 안 된다.
- 실제 브라우저 IndexedDB 엔진, 탭 동시성, 업그레이드 blocked/종료, 저장공간 부족/강제 종료는 미검증.
- companyId 기존 비어 있지 않은 잘못된 값은 자동 수정하지 않는다. integrityFindings 진단은 모든 저장 경로의 외래키 강제가 아니다.
- 확정 급여의 모든 원천정보 수정 조합, 전자신고용 XLSX/PDF 최종 파일과 신고기관 업로드, ATS 전단계 UI 흐름은 미검증.
- v1 사용자 Person이 있는 백업은 안전하게 거부한다. 데이터 손실 없는 전용 변환 지원은 추가 작업이다.
- 일용직 번호 생성/중복 검사 및 여러 기존 편집 경로의 동시성은 별도 검토 필요. 이번 add 변경은 PK 덮어쓰기를 방지한다.

## Person / Employment 정책 검토 (기능 구현 없음)

- 동일 인물의 재입사/사번 변경/복수 고용은 Person을 재사용하고 별도 Employment와 유효기간 이력을 만드는 것이 적절하다. 동명이인은 별도 Person이어야 한다.
- ATS가 기존 인물로 검증된 경우만 연결을 재사용한다. 현재 ATS는 새 Person을 만들며 candidate.personId의 기존 연결을 재사용하지 않는다.
- 정규직과 일용직 역시 동일 인물임이 확인되면 Person 공유가 가능하지만 Employment와 DailyWorker 업무 키/급여 원장은 각각 보존해야 한다. 현재 일용직 등록은 기존 Person ID 덮어쓰기를 거부한다.
- 본인 확인에는 권한 있는 담당자의 확인과 감사기록, 검증된 기존 Person 식별자를 사용해야 한다. 이름, 생년월일, 전화번호, 이메일 하나만으로 자동 판정하지 않는다. 실습용 syntheticIdentifier는 실명 확인 수단이 아니다. 민감식별번호를 새로 수집하는 방식은 도입하지 않는다.
- 정책 결정: 동일인 확인 책임자·증빙·보관 범위, 재입사 사번 재사용 허용 여부/유일성 범위, 동시 복수 고용 허용 여부, ATS 동의/접근 권한, 오연결 해제/정정 승인 절차, 같은 날 복합 발령 처리 방식.
- 현재 구조의 위험: 재입사/ATS 중복 Person으로 인원 집계와 누적 이력이 분산될 수 있다. 사번 중복 차단은 사람 중복 방지가 아니다. 현재 일반등록은 과거 퇴사자 사번도 중복으로 차단한다. 기존 Person 재사용·병합·대량 마이그레이션·삭제는 수행하지 않았다.
